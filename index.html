Behind the build Decisions, boundaries & quality +

Why this exists

Recurring exports make meaningful changes hard to spot. Row order and formatting can add noise. I built the comparison and reconciliation tool around reusable rules.

The engineering choice

Match by identity, use exact decimal operations, and keep file processing in workers. Duplicate keys are reported as ambiguous instead of guessed.

Where the demo stops

This local example compares three sample records and one amount field. The full tool supports CSV/XLSX input, saved profiles, reconciliation and export. Legacy .xls is excluded.

03 / ENGINEERING DECISIONS

The choices behind
the working parts.

Three small decisions with consequences for correctness, offline state and component ownership.

01RECON DESKAmbiguous keys stay visible.+

Implementation

Duplicate keys are reported rather than matched arbitrarily. Composite keys use ordered parts, and identifiers retain leading zeros.

Boundary

The comparison excludes ambiguous keys from matching on both sides.

Explore the project
02OFFLINE FIELD WORKSaved locally is not synced.+

Implementation

Prepared reads and pending edits live in IndexedDB. Saves are sequenced per unit, with at most three concurrent sync operations.

Boundary

The server remains authoritative. Local saving, server confirmation and survey completion are separate states.

Explore the project
03SHARED REACT PACKAGEReusable UI, explicit ownership.+

Implementation

Typed props, callbacks and adapters connect the same visualization components to two applications.

Boundary

Each host owns its authentication, API access, persistence and business validation.
